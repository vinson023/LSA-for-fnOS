## 修复 HTTPS(5667) 打开应用空白破图
- 现象：5666 正常，5667 下点开"LSI 存储管理"内容区空白+破图图标。
- **根因**：桌面入口是**端口服务模式**（`protocol=""`、`port=${wizard_web_port}`）。fnOS 门户前端 `wYe()` 里 `protocol`/`port` 缺省会回退到 `location.protocol`/`location.port`，故 HTTPS 门户下 iframe 变成 `https://<host>:2463/...`，而 2463 只有明文 HTTP → TLS 失败。
- **修复**：改用 **index.cgi 同源路径入口** `/cgi/ThirdParty/{lsa,lsaen}/index.cgi/`。官方文档明确 CGI 入口忽略 `protocol`/`port`、沿用当前访问域名。同机 `fnaudio` 即此模式且 HTTPS 正常，可对标。
- **注册表两处（安装期写入，运行期不重读 `ui/config`）**：`appcenter` 库 `app_service`（app_id=30,id=36）的 `url`/`default_url`；`trim_sac` 库 `entry`（id=157）的 `url`。`app-center` **实时读库**，改完无需重启服务即生效。
- **真机验证**：无头 Chrome（系统 Chrome + 自写 CDP 客户端）登录 5667，点击桌面图标抓到 iframe 实际 src = `https://192.168.5.24:5667/cgi/ThirdParty/lsa/index.cgi/`（同源），LSA 界面完整渲染；5666 回归通过。
- 提交 `5ed44cc`；新增根因文档 `HTTPS_ACCESS_FIX_2026-10-13.md`。

## 用新 FPK 走真实升级流程（真机 192.168.5.24）
- **核心结论：fnOS 不支持本地 FPK 就地升级。** `POST /app-center/v1/install/task` 只要 `appname` 已存在就返回 `10236 = ErrCodeInstalledException`（前端文案「应用已安装」）——**与版本号无关、与运行状态无关**。为排除"同版本限制"假设，专门构建了 `version=8.17.11` 的包（解包核对过），running/stopped 两种状态各试一次，四次全部 10236。
- `trim-cli app update <app> --version <v>` 存在但走云端下载（`POST /v1/download/task`），本地包报 `10030`；`--package-type local` 同样无效。门户 bundle 里没有任何升级专用 API，`install/task` 请求体也没有 `isUpgrade`/`force`/`overwrite` 开关（唯一 `overwrite` 属文件操作枚举）。
- **⇒ 真实部署路径 = 卸载 → 全新安装**，已完整走通并逐项验证。
- **关键验证点通过**：安装流程会**自动**把 `app/ui/config` 的 `url` 写进 `appcenter.app_service`(`url`+`default_url`) 与 `trim_sac.entry`(`url`) —— 两处均为 `://${host}/cgi/ThirdParty/lsa/index.cgi/` 与 `{"path":"/cgi/ThirdParty/lsa/index.cgi/"}`。**改 config 后重装即生效，无需手工改库。**（id/app_id 每次安装递增：36/30 → 67/54 → 69/56，正常。）
- **安装后逐项通过**：LSA+slpd 运行、2463/9000 在听、`fnos_ports.conf`、`installtype=gateway`、`LSA.conf`（readOnly=0 等）、message_zh.js 落地且 6 个 `ui/*/index.html` 注入顺序正确、zh-CN 与 en-US 各 6 个语言资源、静态页与 help 页、4 个兼容软链、`index.cgi` 755。干净系统与脏系统（首次卸载残留之上）都能装。
- **浏览器验收**：无头 Chrome 在 5667 与 5666 各自登录→点图标，iframe src 均为同源 `/cgi/ThirdParty/lsa/index.cgi/`，LSA 中文界面完整渲染（`v008.017.010.000`、远程服务器发现发现本机）。CGI 探活 5667=0.0035s / 5666=0.0006s。
- **发现 7 项新问题**（详见 `UPGRADE_FLOW_VERIFICATION_2026-10-13.md`）：
  1. **开机后看门狗失效（P1）**：`cmd/main` 的 `start_watchdog` 在第 108 行，但第 77–80 行有提前返回；systemd 单元 `enabled` 且开机抢跑（日志实证 `08:33:16` 单元启动 → `08:33:24` `msg="already running" appName=lsa class=start`）→ 提前返回 → 看门狗从未启动。**这正是早前 P1「自愈缺失」的真实成因。** 安装后立即启动的场景下看门狗是正常的。
  2. **卸载残留 `/usr/local/sbin/lsa-fnos-start`（P1）**：两次卸载都留下，`uninstall_init` 只删了 systemd 单元文件。
  3. **`uninstall_init` 的 `|| exit 1` 过于激进（P1）**：`purge_package` 内单点失败会让后续清理全部跳过 → 半卸载状态（deb 仍 `ii`、`/opt/lsi` 仍在、单元文件仍在）。
  4. **卸载偶发中止（P2）**：首次卸载报 `10392 = ErrCodeUninstallInitException`。**未能复现** —— 把 `uninstall_init` 换成带 `set -x` 的 trace 版（放宽 exit 1 / 保留原版逻辑 各一次）复跑，两次都完整成功（3 个 deb purge 全 rc=0、`/opt/lsi` 完全删除）。独立验证 `prerm` 也无问题（`prerm_exit=0`）。appcenter `error.log` 反复出现 `hook error ... nil pointer dereference`，推测为其钩子执行器不稳定。
  5. **`ExecStop` 缺 `cd`（P2）**：`nginx -s stop -p .` 的 `-p .` 被解析成 systemd 的工作目录（`/`）→ 每次停止都报 `open() "./conf/nginx.conf" failed` 并把单元打成 `failed`；`daemon-reload` 不清除该状态。安装后单元即 `failed`+`enabled`。
  6. **`upgrade_init`/`upgrade_callback` 是死代码（P2）**：没有就地升级路径，永不被调用，其"升级保留配置"职责完全落空。目前配置"看起来没丢"只是因为首次卸载中止、`/opt/lsi` 被意外保留 —— 属侥幸。**建议迁到 `uninstall_init` 备份到 `$TRIM_PKGVAR`（卸载后仍保留，实测）+ `install_callback` 还原。**
  7. **厂商硬编码字符串无法本地化（P3，非本项目缺陷）**：`Gateway - Authenticate`、`Load More`、`HOST` 不在 `message_en.js` 键集中，被编译进 GWT 模块，`message_zh.js` 覆盖层无法触及。zh 键数 2347 vs en 2351。
- `appcenter.app.is_systemd_uint` 对 lsa 为 `f` —— fnOS **不认为**本应用是 systemd 单元应用，那个单元是项目自行附加的，脱离了 fnOS 生命周期管理。
